## 3. 本次 D14-R1 / R2 修改

### D14-R1 — 当前已绑定 Metadata Snapshot 边界

Resolution 只允许消费当前租户、已启用 DataSource 对应的 Metadata。

因此遵循正式开发计划的核心原则：

```text
用户只绑定数据库 A
    ↓
当前 Metadata Snapshot 只有 A
    ↓
A 中不存在供应商/物料主表
    ↓
不猜主表、不硬编码、不生成 JOIN
```

当用户后续绑定数据库 B 并重新扫描 Metadata：

```text
A + B Metadata Snapshot
        ↓
重新 Resolution
        ↓
如果形成稳定 Master Evidence
        ↓
允许升级为 MasterJoin
```

跨 DataSource Federation 仍未开放；当前 QueryPlan/SQL Runtime 仅执行同一 DataSource 内的 MasterJoin。

### D14-R2 — Master Evidence 阈值校准

`MasterJoinThreshold` 从 `0.80` 调整为 `0.65`，避免已存在稳定 Metadata Master Evidence 时因二次评分门槛过高而错误降级为 DirectKey/NotResolved。

仍保留：

- Primary Key 约束；
- Dimension Semantic Evidence；
- Master Candidate ambiguity gap；
- 同 DataSource 才允许 Executable；
- 不存在稳定 Master Evidence 时安全降级 DirectKey；
- Evidence 不足时 BLOCK。

## 4. SQL Builder 已完成事实

D14 的 SQL Builder 实现已经完成，不再作为后续缺口重复修改。

当前 `SqlQueryBuilder`：

- 只消费 `QueryPlan.Joins`；
- 不硬编码“物料”“供应商”等业务主表；
- 不自动推断 JOIN；
- DirectKey 不生成 JOIN；
- MasterJoin 由已确认 Resolution 生成 `QueryPlan.Joins` 后动态生成 SQL；
- JOIN 引用的表必须已存在于 QueryPlan Metadata Tables。

## 7. D14 Exit Gate 前置要求

不得因为某个 Golden Case 当前 Metadata 中不存在 Master Table 就修改代码硬编码该主表。

正确判定必须是：

```text
Metadata 不存在
    → 不 Join
    → DirectKey（有稳定 Key）或 BLOCK（无稳定 Key）

Metadata 存在且形成稳定 Master Evidence
    → MasterJoin
    → 同 DataSource 才允许 Runtime Executable

Metadata 存在但 Evidence 不稳定/竞争
    → BLOCK
```
