## 3. D14-R5 — 同一 Dimension 多物理表达候选归一化

### 根因

当前 Metadata 对“物料”可能同时存在：

```text
material_id
material_code
material_name
```

这些字段并不表示三个不同业务 Dimension，而是同一 Dimension 的不同物理表达：

```text
物料
├── Identifier：material_id / material_code
└── Display：material_name
```

旧实现将所有候选直接放入同一个 `AmbiguityGap` 比较池，因此 `material_code` / `material_id` 与 `material_name` 分差不足时会被错误判定为 Ambiguous。

### D14-R5 修改原则

1. 仍然只消费当前已绑定/启用 DataSource 的 Metadata。
2. 不硬编码“物料”“供应商”主表。
3. 不硬编码业务字段名称。
4. 不新增主表猜测。
5. 将事实表候选按物理角色分层：
   - Identifier / PrimaryKey：用于 MasterJoin 的事实侧连接键；
   - 非 Identifier：在没有 Master Evidence 时可作为 DirectKey 的直接展示/分组字段。
6. Ambiguity 只在同一物理角色内部判断。
7. 若存在稳定 Master Evidence，优先 MasterJoin。
8. Master Evidence 竞争时仍然 BLOCK，不降级绕过。
9. 没有 Master Evidence 时，优先使用稳定的直接展示字段；没有展示字段才退回 Identifier。
10. DirectKey 仍然不生成 JOIN。

### GQ-003 / GQ-006 预期

对于当前已绑定 Metadata 中的事实表：

```text
wms_storage_receipt_info
├── material_id
├── material_code
└── material_name
```

如果不存在稳定 Master Evidence：

```text
物料
 ↓
DirectKey
 ↓
使用当前事实表已存在的稳定物料字段
 ↓
不生成 QueryJoin
```

如果用户随后绑定数据库 B，且 B 的 Metadata 出现稳定物料主表：

```text
A + B Metadata Snapshot
 ↓
Master Evidence
 ↓
同 DataSource
 ↓
MasterJoin
```

跨 DataSource Federation 仍不开放；跨库 Master Evidence 必须保持 `NotExecutable`。

## 4. SQL Builder 已完成事实

D14 的 SQL Builder 实现已经完成，不再作为后续缺口重复修改。

当前 `SqlQueryBuilder`：

- 只消费 `QueryPlan.Joins`；
- 不硬编码“物料”“供应商”等业务主表；
- 不自动推断 JOIN；
- DirectKey 不生成 JOIN；
- MasterJoin 由已确认 Resolution 生成 `QueryPlan.Joins` 后动态生成 SQL；
- JOIN 引用的表必须已存在于 QueryPlan Metadata Tables。

## 7. D14 Exit Gate 前置要求

不得因为某个 Golden Case 当前 Metadata 中不存在 Master Table 就修改代码硬编码该主表。

正确判定必须是：

```text
Metadata 不存在
    → 不 Join
    → DirectKey（有稳定 Key/展示字段）或 BLOCK（无稳定证据）

Metadata 存在且形成稳定 Master Evidence
    → MasterJoin
    → 同 DataSource 才允许 Runtime Executable

Metadata 存在但 Evidence 不稳定/竞争
    → BLOCK
```
