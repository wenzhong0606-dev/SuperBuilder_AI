1. 引言

1.1 编写目的

本文档旨在为 SuperBuilder AI Native 企业智能平台提供系统性的总体设计方案，明确平台的建设目标、总体架构、核心子系统、数据架构、技术选型、安全机制及非功能性要求，为后续详细设计、开发、测试及部署实施提供指导依据。

1.2 项目背景

随着企业数字化建设的深入，多数企业已积累了包括 ERP、MES、WMS、CRM、PLM、财务系统、数据仓库等多种业务系统。传统企业软件主要解决数据记录、流程管理和业务执行等基础需求，但面对日益复杂的业务环境，企业迫切需要更高层次的智能能力：

  • 自动理解业务：从数据中识别业务语义与逻辑
  • 自动分析数据：多维度、跨系统的智能数据分析
  • 自动生成应用：根据业务需求动态生成可用的企业应用
  • 自动辅助决策：提供可执行的洞察与建议

为此，需建设新一代 AI Native 企业智能应用平台，将大语言模型、语义模型、知识增强与低代码运行时深度融合，重塑企业与软件的交互方式。

2. 总体建设目标

2.1 业务目标

构建一个能够“理解企业、分析企业、生成应用、辅助运营”的智能平台，实现从企业数据到知识、智能、应用直至业务执行的完整闭环，显著降低企业数字化门槛，提升决策效率与业务敏捷性。

2.2 技术目标

建立如下技术闭环链路：

flowchart LR A[企业数据] --> B[企业知识] B --> C[企业智能] C --> D[企业应用] D --> E[企业执行] E -.->|反馈优化| A

确保各环节通过 AI 自动化衔接，减少人工干预，提升系统智能化水平。

2.3 产品目标

以典型场景为例：

  • 用户输入：“查询今年华东区销售下降原因”
  • 平台自动完成：
    1. 理解问题意图与业务语境
    2. 匹配业务指标与维度
    3. 查询并整合多源数据
    4. 生成分析结论与可视化图表
    5. 提出改进建议
    6. 支持一键执行相关业务动作

3. 设计原则与约束

3.1 设计原则

原则说明
AI Native First所有核心能力以 AI 为原生驱动力，AI 贯穿数据理解、分析、生成全流程
Semantic First以企业语义模型为核心资产，屏蔽底层数据异构性
Agent Driven将复杂任务拆解为 Agent 协作，实现自主规划与执行
Runtime Based提供统一的低代码运行时，支持动态组件渲染与应用执行
Low-Code Generated应用生成优先采用模型驱动和配置化方式，降低开发成本
Clean Architecture分层解耦，领域层独立于基础设施，保障可测试性与可维护性

3.2 技术约束

  • 后端基于 .NET 10 生态
  • 前端采用 Blazor / Razor / MAUI 技术栈
  • AI 模型优先选用 Qwen 系列
  • 向量检索基于 Qdrant
  • 关系数据库支持 SQL Server、MySQL、PostgreSQL
  • 部署环境支持容器化（Docker/Kubernetes）

5. 系统分层设计

5.1 用户界面层（Presentation Layer）

职责：负责与用户交互，展示数据、接收输入、渲染动态组件。

  • 技术实现：.NET 10 + Blazor (WebAssembly/Server) + MAUI (移动端) + Bootstrap 5
  • 主要项目：SuperBuilder.Web、SuperBuilder.Shared、SuperBuilder.Maui
  • 支持多端适配与响应式布局，提供统一的 Copilot 交互入口。

5.2 应用服务层（Application Layer）

职责：业务流程编排与组合，不包含业务逻辑，调用领域层能力与基础设施接口。

  • 核心服务：BIConversationService、ComponentService、WorkflowService、AgentService
  • 特性：无技术依赖，面向接口编程，便于单元测试与替换。

5.3 领域层（Domain Layer）

职责：核心业务模型与规则，是平台的业务内核。

核心领域模型分组：

  • 企业基础模型：Tenant, User, Role, Permission
  • 数据智能模型：DataSource, MetadataTable, MetadataColumn, MetadataSemantic
  • AI 模型：Agent, AgentTask, Knowledge, Prompt
  • Low-Code 模型：Component, ComponentDefinition, ComponentVersion

领域层不依赖任何外部框架，仅包含业务实体、值对象、聚合根、领域服务。

5.4 基础设施层（Infrastructure Layer）

职责：提供所有外部技术实现，包括数据持久化、AI 调用、向量检索、缓存、文件存储、API 网关等。

  • 数据库访问（EF Core + Dapper）
  • AI 服务调用（Qwen API）
  • 向量数据库（Qdrant Client）
  • 缓存（Redis）
  • 文件存储（OSS / 本地）
  • 外部系统集成（API Gateway）

8. 接口设计

8.1 内部接口

各层之间通过依赖倒置（接口抽象）交互，领域层定义接口，基础设施层实现。例如：IMetadataRepository、IAiModelClient、IVectorStoreClient。

8.2 外部接口

接口类型用途协议
RESTful API供前端及外部系统调用HTTPS + JSON
WebSocket实时对话与流式 AI 响应WSS
SDK供第三方扩展组件或 Agent 工具.NET 包

8.3 API 设计规范

  • 遵循 RESTful 风格，资源命名采用复数形式
  • 统一响应格式：{ code, message, data, timestamp }
  • 认证方式：Bearer JWT
  • 版本管理：URL 路径版本（如 /api/v1/...）
  • 错误码体系：按模块划分，详见《API 设计规范》文档

9. 安全架构设计

9.1 身份认证

支持多种认证方式：JWT（默认）、OAuth 2.0 / OIDC（对接企业 SSO）、可扩展第三方身份源（如 Azure AD、钉钉、企业微信）。

9.2 权限模型

采用基于租户的多级权限体系：

flowchart LR A[Tenant 租户] --> B[Role 角色] --> C[Permission 功能权限] --> D[DataScope 数据范围控制]
  • 功能权限：控制菜单、按钮、API 的访问
  • 数据权限：控制用户可见的数据行/列范围（基于行级安全）

9.3 数据安全

  • 传输加密：全链路 TLS 1.3
  • 敏感数据存储：字段级加密（如手机号、身份证）
  • 脱敏显示：日志与前端展示按策略脱敏
  • SQL 注入防护：参数化查询与 ORM 框架保障

9.4 审计日志

记录关键操作（登录、查询、数据修改、AI 调用），日志内容包括操作人、时间、IP、操作类型、结果、敏感信息脱敏后存储，日志保留至少 180 天。

10. 非功能性设计

10.1 性能目标

指标目标值
页面加载时间< 2 秒（首次）
语义搜索响应< 500ms
SQL 生成时间< 3 秒
AI 对话首字响应< 5 秒（流式输出）
并发用户数支持 500 并发（初期）

10.2 可用性

  • 系统可用性目标：99.9%（年度宕机 < 8.76 小时）
  • 关键组件（数据库、AI 服务）采用高可用部署
  • 故障自动恢复与重试机制

10.3 可扩展性

支持以下维度的水平扩展：

  • 新 AI 模型：通过适配器模式接入不同大模型
  • 新数据库：通过方言层扩展 SQL 生成
  • 新组件：通过组件注册机制添加前端/后端组件
  • 新 Agent 工具：通过工具注册 API 扩展 Agent 能力

10.4 可维护性

  • 代码遵循 Clean Architecture，业务逻辑与技术实现解耦
  • 提供详尽的技术文档与 API 文档
  • 统一日志格式，支持结构化日志（Serilog）
  • 支持动态配置热更新（基于 Apollo 或 Nacos）

10.5 监控与运维

  • 接入 Prometheus + Grafana 监控体系，监控系统资源、应用性能、业务指标
  • 链路追踪（Jaeger/Zipkin）用于分布式调用分析
  • 告警规则：CPU/内存超阈值、接口错误率、AI 服务超时等
  • 日志集中管理（ELK 或 Loki）
