## 上午：Ask 跨数据源选错表 + 语义细化 Low 置信度诊断

- 现象：单数据源（wms）时「最近十条入库凭证」正确查 `wms_storage_receipt`；添加 pms 等多数据源后 Ask 生成 SQL 选了 `pms_complete_storage`；用语义细化输入「应该查询的wms_storage_receipt表」重查 → `QueryPlan Confidence 为 Low，Score=0.429，不足以进入 SQL Builder`。

- 根因 2（细化反而 Low，两个叠加）：
  1. `AskController.TryExtractTableCorrection` 触发词仅「应该是/应为/改成/改为/查询表/表错/错表/表不对/使用表/用表」——用户输入「应该**查询的**wms_storage_receipt表」一个都不含 → 强化句「查询物理表必须使用 wms_storage_receipt」未追加；

## 设计答疑：异构租户如何确认字典结构（10:53）

- 用户疑问：其他租户/用户绑定的数据结构与己方不一致，如何确认字典结构？
- 结论：字典结构**绝不全局假设**，按每个 `DataSourceId`（已带 `TenantId`）在扫描时就地发现，以【角色】(Code/Name/Type) 而非字面列名存储；异构是常态而非例外。
- 三层信任、各自独立（均 per DataSourceId）：
  1. 列注释解析：三库扫描已抓 `ColumnComment`（MySqlMetadataReader 证），注释内含 `1=采购,2=调拨` 图例或引用声明 → 直接成该列 ValueMap/FK，零手工、天然随租户 schema。
  2. 字典表启发式：扫描时按 2-4 列 + (code+name+type) 形态 + 小/中行数 + 名称含 dict/code/enum 检测候选字典表，记录其【角色映射】入 `MetadataDictionaryConfig`（仍是 code/name/type 角色，非字面列名）→ 租户B用 key/val/group 也只存角色，引擎读角色。
  3. 跨源FK链接（WMS→PMIS）：schema 无法揭示（分属不同数据源），只能**声明/学习**，存为 tenant+user 规则，须目标 DS ∈ authorizedDataSourceIds 才应用。
- 运行时自检：Enrich 取数前发 `SELECT code,name FROM dict LIMIT 1` 校验角色映射在该 DS 真实存在；失配/越权 → 降级（学习映射→原值），**绝不抛错**，并标记待重扫。
- 无字典租户（仅WMS无PMIS）：不产生 dict 配置 → 该列落 ValueMap(注释)/学习映射/原值，优雅降级。
- 隔离底线：每个 `MetadataDictionaryConfig`/`QueryCorrectionRules` 带 `TenantId`；即便两租户都有同名 `wms_storage_receipt`，其 FK/字典绑定互不影响。

## 傍晚续 2：多表 JOIN 下 del_flag ambiguous 修复（SQL 列限定）

- 用户报错（截图）：`查询最近十条入库记录` → `查询失败：Column 'del_flag' in where clause is ambiguous`。当时 SQL：

  2. `SqlQueryBuilder.ResolveTableName` 增 `allowMainTableFallback`，**仅 WHERE / ORDER BY / GROUP BY 开启**（多表无归属 → 锚定主表 `Tables[0]`，口径同 `QueryPlanMetadataValidator.FindColumns` 的「主表优先」）；**SELECT 投影刻意不开启**——`RowLevelSecurityTests.SqlBuilder_QualifiesRlsAcrossJoinAndAggregate` 锁定了「投影无法解析即裸列名」契约（先全开导致该测试红，收窄后恢复）；
  3. 新增 `QualifyIntentField`，处理 `Intent.OrderBy` / `Intent.Dimensions` 的裸列名（单表保持原样，多表锚主表）。
