## A4 重构后 GQ-010 确定性回归修复 (2026-08-28)

- 现象: A4 上帝类拆分 + P3 重建后 Golden 17/18，GQ-010 FAIL（deterministic，两次 run 的 confidenceScore 完全一致 0.4997...）。
- 根因: `src/Application/BiQuery/QueryPlanBuilder.SemanticResolution.cs` 的 `ApplyFilterResolutions` 用 `n=Math.Min(plan.Filters.Count, bindings.Count)` 仅按**索引**重写前 n 条 Filter。GQ-010 "查询2025年入库数量最多的前10个物料" 运行期 LLM 多产出 Filter（plan.Filters.Count=2），而 Semantic Resolution 仅 1 条绑定(bindings.Count=1) → 仅索引0被重写为 `come_time`，索引1残留语义名 `入库日期` → Validation 报 `FilterFieldNotFound`，但 Evaluation 因只校验"期望 Filter 是否存在"而 PASS（come_time 被匹配），于是卡在 17/18。
- 修复: 将"按索引 min 条重写、其余忽略"改为**按 SemanticText 语义对齐 + 丢弃无绑定幻影 Filter**：
  - 对每个 Runtime Filter 优先按 SemanticText（回退 Field 同名）匹配一条未使用 Resolution 绑定 → 重写 Field 为物理列；
  - 匹配失败者视为 LLM 幻影（无物理落点），从 plan.Filters 逆序 RemoveAt 丢弃；
  - 新增私有 `MatchFilterBinding(bindings, runtime, used, positional)`（SemanticText → Field 同名 → 位置回退 三级优先级）。
  - 该策略对 1:1、Runtime 少于/多于 Resolution 三种漂移均安全，且契合 C.13.2 "只消费已确认 Semantic Resolution"。
- 验证: `dotnet build -c Debug` → 0 error。复跑 `golden_run_20260828_fix.json` → **GQ-010 转 PASS（conf 0.8，validation errors=[]）**，修复确认有效。
- 注意: Golden `/run` 端点缓冲整个响应直到 18 case 全跑完（每 case 多次 Qwen LLM 调用 ~13s/次），单次 HTTP 约 330s；用后台 curl + 长 max-time 跑。SQL Server(localhost/live/root/SuperBuilder_Platform) 与 Qdrant(localhost:6333/superbi_metadata=961点) 均在线。

## GQ-008 幽灵维度确定性加固（与 GQ-010 对称）(2026-08-28)

- 现象: GQ-010 修好后同一次 run 变成 GQ-008 FAIL（conf 0.4604），validation error = `DimensionFieldNotFound` 且 field 为**空字符串**；evaluation 侧 metrics/queryShape/semanticEvidence 全 1.0，仅 dimensions 打 0（"No dimensions were expected, but runtime produced dimensions"）。历史记忆早已标注 GQ-008「幽灵维度」为 LLM 抖动项（run1/run2 曾 PASS conf 0.8）。
- 根因链（确定性可复现）:
  - `BuildResolvedPlanSkeleton`（SemanticResolution.cs:76-77）创建 Runtime 维度时**只**填 `SemanticText`，`MetadataColumnId=0`/`ColumnName=""`；维度的物理落点**只能**来自 `ApplyDimensionBinding`。
  - GQ-008「统计不同供应商数量」Golden 不期望 Dimension → `resolution.Dimensions.Count==0`，而 `ApplyDimensionResolutions` 首行即 `if (bindings.Count == 0) return;` → LLM 偶发多产出的空维度原样留在 `plan.Dimensions`。
  - `QuerySemanticValidator.ValidateDimensions` 以 `MetadataColumnId` → `ColumnName` 查列，两者皆空 → `DimensionFieldNotFound: ""` → Repair 无候选 → Decision Gate BLOCK → FAIL。
- 修复（`ApplyDimensionResolutions` 与 `ApplyFilterResolutions` 完全对称）:
  - `bindings.Count == 0` 时不再直接 return，改为 `plan.Dimensions.RemoveAll(IsUnboundDimension)` 清除幻影维度；
  - 数量/顺序漂移不再硬抛 `InvalidOperationException("Dimension 数量不一致")`，改为：SemanticText 对齐 → 丢弃无绑定幻影 → 用**未消费**的 Resolution 绑定补全新维度（Resolution 是权威绑定）；
  - 新增 `IsUnboundDimension(dim)`（`MetadataColumnId<=0 && ColumnName 空`）与 `MatchDimensionBinding(...)`（SemanticText 精确 → SemanticText/ColumnName 与物理列同名 → 位置回退；**空维度禁止位置回退**，否则会把空维度错绑到无关 Resolution 维度）。
- 通用教训: 凡「Runtime(LLM) 集合 × Resolution 绑定集合」的对齐点，都必须同时处理 3 种漂移（1:1 / Runtime 少 / Runtime 多），并对「无绑定即不可执行」的 Runtime 元素做丢弃，而不是 return/忽略/抛异常。Filter 与 Dimension 现已统一为该模式；Metric/Order 侧仍是索引 min 写法，为后续同类抖动的潜在隐患点。
- 验证: build 0 error / 10 warning（既有 nullable）。**Golden 全量复跑 18/18 PASS**（`Evaluation/artifacts/golden_run_20260828_fix2.json`：passed=true, decision=PASS, expectedOutcomePassed=18/18, scorecard overall/positive/negative/ambiguous/unresolved 全 1.0, failedGates=[], 18 case 的 validation errors 全空）。A4 + P3重建 后的回归基线恢复到 D18 黄金状态。
- 期间失败序列（供追溯）: A4 后 run1/run2 = 17/18（GQ-010 FilterFieldNotFound 确定性）→ 修 Filter 后 fix run = 17/18（GQ-008 DimensionFieldNotFound 幽灵维度）→ 修 Dimension 后 fix2 run = **18/18**。
