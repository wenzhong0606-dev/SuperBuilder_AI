## Qdrant 闪退修复（2026-09-14 14:12）
- 用户双击 `qdrant.exe` 闪退。实跑捕获 panic：`Failed to load local shard "./storage\collections\superbi_metadata\0": Wal error: Can't init WAL: Kind(WouldBlock)`。
- 根因：残留 `qdrant.exe` 进程（PID 26544，65MB）持有 `superbi_metadata/0/wal/.wal` 独占锁；新实例加载同 shard 时 WAL 锁冲突 → panic 闪退。`.wal` 文件本身 0 字节（Sep 1），锁在 Windows 文件句柄上（非文件内容）。
- 修复：`taskkill.exe /F /IM qdrant.exe` 强杀所有残留 → 释放 WAL 锁 → 单实例重启。受管后台任务重启（task_id 3GbQob，PID 57384）后 shard 正常恢复，REST/gRPC 监听 6333/6334。
- 验证：curl `GET /collections/superbi_metadata` → `status:green, points_count:1061, segments_count:8`，向量数据完好（演练基线 1061 点）。
- 防复发：勿同时开多实例；异常退出后用 `taskkill /F /IM qdrant.exe` 清残留再启动。WAL 锁随进程死亡释放，单实例自愈有效（已实测）。
- 坑：`(./qdrant.exe &)` 子shell后台启动会被 Bash 调用结束清理；必须用 run_in_background 受管任务才能跨调用存活。

## 扫描生成语义慢的根因（代码审计 2026-09-14 14:51）
- 链路：`MetadataScannerService.ScanAsync` 五阶段（读结构→同步→**生成语义**→**向量索引**→保存）。慢在阶段3/4。
- 阶段3 生成语义：`MetadataSemanticService.GenerateBatchAsync` 串行 `foreach(columns.Chunk(50))`，每批一次 `QwenService.GenerateSqlAsync`（Qwen LLM，默认超时180s）。批间 await 串行、无并发；N字段→ceil(N/50)次HTTP。
- 阶段4 向量索引（最慢）：`MetadataVectorService.IndexAsync` 逐表×(1表+列×2) 串行调 `QwenEmbeddingService.GenerateAsync`（单条 input，无批量）+ `Qdrant.UpsertAsync`（逐条，无批量）。字段越多往返越多，无并发。
- 三外部依赖（Qwen/Embedding/Qdrant）每次调用独占一个 HTTP 往返，全部 await 串行叠加。首次扫描全字段 Semantic==null 触发全量生成+全量索引，故感觉巨慢；字段总量随用户多绑定数据源上升而放大。
- 优化方向（未实施）：阶段3 批间并发/增大批大小；阶段4 改批量 embedding（input 数组）+ Qdrant 批量 upsert + 表内并发；检索侧 `SearchByKeywordAsync/Substring` 全表 `ToListAsync` 内存过滤（非扫描链路但同样随语义量变慢）。
