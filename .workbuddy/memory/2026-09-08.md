## 登录根因定位 + E2E 改走 API 登录（2026-09-08 收尾）
- **用户实测两问题**：① 登录页下拉框无「平台治理」租户；② demo 登录提示"请求过于频繁（429）"。已逐一从源码定位根因。
- **根因①**：`platform` 租户被登录 UI **刻意排除**——`AuthController.LoginOptions`(`Where(x=>x.TenantCode!="platform")`) 与 `TenantByCode` 两 GET 辅助端点都排除 `platform`；但 **`POST /api/auth/login` 只用数字 `TenantId` 校验、不排除 platform**（`AuthController.Login:67-74` 仅查 `Id==TenantId && Enabled`）。`platform-admin` 由 `PlatformAdminBootstrapper.CreateAsync` 种进 platform 租户（`TenantId=5, TenantCode=platform`）。即 platform 治理账号**不走普通多选租户 UI**，须用 API 直接登录。
- **根因②**：429 来自 `RateLimitMiddleware`（默认 `LoginLimit=10`/60s、`GlobalLimit=120`/60s；限流键匿名=IP+UA 哈希）。本机 localhost 所有请求同回环 IP → 共用一个 IP 桶，浏览器预取+多次点击易超 10 次 → 触发。**默认 `MemoryRateLimitStore`（进程内存）→ 重启 Web 实例即清零**；若配了 Redis 存储则需 Flush 或等过窗口。修法：`appsettings` 调大 `RateLimit:LoginLimit/GlobalLimit` + 重启。
- **SQL 确认**：`SELECT Id,TenantCode,...` → `1=WMS`(demo 属此)、`5=platform`(platform-admin 属此)。故 E2E env `SB_E2E_TENANT=5`/`SB_E2E_READER_TENANT=1` 对 **API 登录恰好正确**（API 认数字 Id）。
- **E2E 改动**：新增 `LoginHelper.ApiLoginAsync(page,user,pwd,tenantId(long))`——经浏览器 `fetch('/api/auth/login',{Username,TenantId,Password})` 取令牌 → 构造与 `AuthStore.AuthSnapshot` 严格一致的 `sb_auth_v1` JSON 快照（字段 `Token/TenantId/HomeTenantId/UserId/Username/Permissions/AvailableCultures/DefaultCulture`）→ 注入 localStorage → 进 `/ask`。`AppRuntimeE2ETests` 两用例均由 `LoginHelper.LoginAsync`(UI) 改为 `ApiLoginAsync`，管理员(5)/读者(1) 均经 API 登录（规避 UI 排除 platform + 登录形态/限流差异）。E2E 工程重编 **0 错误**。
- **遗留风险（执行前需确认）**：`platform-admin` 须持有 `app:publish`(及 Ask 所需权限)，发布按钮 `PermissionGuard(app:publish)` 才会显示，否则用例会在发布步骤失败；若平台角色未授予 `app:*`，需给 platform-admin 补权限或用具备 app 权限的租户内管理员。
- **结论**：两问题均非代码缺陷——① 是平台租户 UI 隔离设计（E2E 改 API 登录绕过），② 是限流阈值过低（调大+重启即可）。本地用户执行 E2E 步骤同前，但登录改为 API 路径、env 的 5/1 保持不变。
