## M0 Ask 跨数据源选表歧义 — 修复落地与验证

### 根因（已用真实检索数据证实，非推断）
用户用「改成 wms_storage_receipt 表」细化时：
1. 「改成」确实触发 `AskController.TryExtractTableCorrection` 并拼入合成问题「查询物理表必须使用 wms_storage_receipt」。
2. `wms_storage_receipt` 一直在 top-10 内（实测 rank4/9，ds1）。
3. 真正失效点：`_dataSourceScope.ScopeAsync` 在选表前按授权/请求数据源范围把目标表所在 ds1 收敛掉 → `TableSelector.ResolveExplicitTableOverride` 在收敛后候选里找不到该表 → 返回 null → 退化正常评分 → pms(ds4) 胜出 → 计划同原问题 → 同一分数 0.429 Low。

### 修复（6 处，已落盘，编译通过 0 error/0 warning）
- `IMetadataSemanticSearchService.ResolveTableByNameAsync`：新增接口方法，并加默认实现（返回 null）以免破坏既有测试 Fake。
- `MetadataSemanticSearchService.ResolveTableByNameAsync`：用 `_context.MetadataTables` + 已授权 `authorizedDataSourceIds` 按表名确定性找回（守住跨租户/数据源安全）。
- `TableSelector.SelectBestTable` / `ResolveExplicitTableOverride`：两阶段锁表 —— 先候选内匹配，候选无则调 `tableResolver(correctedName)` 从全授权目录找回；新增 `PhysicalTableNameRegex` / `ExtractCorrectedTableName`。
- `QueryPlanBuilder.TableSelection.cs` + `QueryPlanBuilder.cs`：把 `authorizedDataSourceIds` 透传到 `SelectBestTable` 的 `tableResolver`（首轮编译失败：`authorizedDataSourceIds` 不在 partial 作用域，已修复）。
- `QueryPlanConfidenceEvidence.TableCorrectionHonored` + `QueryPlanConfidenceService`：`IsTableCorrectionHonored`（纠正短语 + 计划主表名同现于问题）为真时置信度保底至 Medium（score≥0.8 才 High）。
