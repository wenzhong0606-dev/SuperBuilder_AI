## Qdrant 依赖边界

项目现有 compose 使用容器；不能把该配置当作 Windows 原生安装证据。首批应用可连接已有 Qdrant 服务，实际地址、版本、存储和备份位置须在安装验证前登记，不记录凭据。全部组件同机原生安装目前尚未验证，不能宣布支持。

仓库 compose 的 v1.14.1 与既有演练记录的 1.19.0 不一致，版本统一仍归 ENV-01。安装验证前必须选定并记录实际服务版本，不直接套用旧 compose。官方安装参考：[Qdrant installation](https://qdrant.tech/documentation/installation/)。

## 安装验证步骤

1. 记录目标主机 OS 版本、CPU、内存、磁盘、网络以及部署账号权限；本地开发机不自动等同目标服务器。
2. 固定候选 SHA，分别生成 API/Web 发布产物，记录运行时与依赖版本。
3. 确认 Windows 托管方式及开机启动、停止、重启和日志路径；不把能用命令行启动等同服务托管已完成。
4. 通过受控配置注入密钥与连接信息，确认应用到 SQL Server、Qdrant、模型和业务库的连接；不打印配置值。
5. 在隔离数据库验证空库安装及已有库升级；缺迁移时验证业务请求拒绝。
6. 验证 HTTPS 登录、数据源预测试/保存/扫描、Ask、成果保存重载及权限负向案例。
7. 验证应用重启后的登录、会话失效提示、权限及数据恢复行为。
8. 按交接自检表由非开发人员完成安装和升级记录；尚未执行的项不得标通过。

## 容量测量准备

先做探索性测量，按 1、5、10 个并发请求分档；这不是支持人数承诺。每档固定数据快照、问题集、权限、缓存状态及模型配置，记录请求总数、成功/失败/超时/429、P50/P95、CPU、内存、磁盘和供应商用量。成功请求与失败请求延迟分别报告，不能靠快速失败降低 P95。

先区分无模型接口与真实 Ask 请求；离线兜底或固定响应结果不得替代真实模型性能。执行前锁定请求上限、持续时间、模型预算与隔离环境；不向未确认的客户业务库施压。正式验收仍需 O2 的业务目标，测量结果不得自动改写目标。
